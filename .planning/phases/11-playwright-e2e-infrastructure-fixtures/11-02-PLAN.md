Land the narrow, env-gated rate-limit bypass mechanism (INFRA-06) inside the existing Fastify plugin — never a blanket disable — using `@fastify/rate-limit`'s own `allowList` function option. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> API rate-limit hook | An HTTP header (`x-e2e-bypass`) can request exclusion from rate limiting |
| operator config -> runtime | Where the bypass secret may (and may not) be set |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-01 | Elevation of Privilege | `E2E_RATE_LIMIT_BYPASS_SECRET` bypass gate | high | mitigate | Secret read directly from `process.env`, never added to `envSchema`/`.env.example` (Task 2 guard test proves absence); `allowList` omitted entirely when the secret is unset, so dev/prod behavior is unchanged (Test C proves a leaked header with no configured secret still gets a real 429). |
| T-11-02 | Spoofing | `x-e2e-bypass` header value | high | mitigate | Strict equality against a per-run-generated secret (generation happens in the compose/CI plans); a wrong/absent header is not excluded. Behavior B proves a missing header still hits the real limit. |
</threat_model>
