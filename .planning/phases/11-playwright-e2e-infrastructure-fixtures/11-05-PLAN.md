<objective>
Deliver the reusable per-role `storageState` auth fixture (INFRA-04): one real magic-link login round trip per role at suite start, saved and reused so every downstream authenticated suite (Phases 13–17) skips the login round trip entirely. Prove it with a fresh-context reuse spec for both Admin and Member.

Purpose: Re-authenticating per spec file is the dominant cost of an E2E suite (RESEARCH Pitfall/Pattern 2). This fixture pays the login cost once per role per run. RESEARCH already proved (Pitfall 2 RESOLVED) that better-auth stores the session only in an httpOnly cookie — apps/web has zero sessionStorage and zero auth-related localStorage — so cookie-capturing `storageState` reuse is safe by construction; this plan exercises and asserts that.
Output: `auth.setup.ts`, the setup + chromium-admin + chromium-member projects, and a green `storage-state.spec.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser context -> app session cookie | storageState captures the live httpOnly session cookie |
| saved storageState file -> disk | `.auth/*.json` are live credentials at rest |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-02 | Information Disclosure | `playwright/.auth/*.json` (live session cookies) | high | mitigate | Treated as live credentials: gitignored (11-01), regenerated every run by the setup project, never a CI cache artifact, never committed (RESEARCH Security Domain V3). Verified via git-ignored status in Task 1. |
| T-11-08 | Spoofing | reused storageState maps to the wrong role | medium | mitigate | storage-state.spec asserts a role-specific UI signal per project (Team nav present for admin, absent for member), so a mis-captured/mismatched session fails the spec rather than silently passing. |
</threat_model>
