## Phase Goal

**As a** team operator, **I want to** sign in to Kurzly with a magic link and land in a themeable dashboard shell whose every domain-scoped action is authorized server-side, **so that** I can manage short links securely on my own infrastructure.

> This plan builds the deny-by-default authorization core (D-02) that gates every future domain-scoped route. It has zero callers in Phase 2 by design — its correctness comes entirely from the unit suite here.

> **Requirements note:** This is foundational authorization infrastructure mandated directly by the Phase 2 goal (D-02), not by a v1 REQUIREMENTS.md ID. The `requirements` field uses the `foundational-infrastructure` marker rather than a numbered REQ-ID. The 7 Phase-2 v1 requirements (AUTH-01..04, UI-01..03) are each covered by plans 02-01/02/04/05/06. The helper is built here ahead of its downstream enforcement (Phase 9's TEAM-06 negative-test suite) per the roadmap decision, but that is a forward-reference for context only — TEAM-06 is out of Phase 2 scope.

<objective>
Build and unit-test the domain-scoped authorization helpers `requireDomainAccess` and `scopedDomainIds` (D-02) via strict TDD (RED → GREEN → REFACTOR) against the real-Postgres harness, with a frozen signature so Phases 3–9 depend on it without churn.

Purpose: This is the security abstraction the whole roadmap is built around — centralizing role-hierarchy checks here prevents the scattered ad-hoc authorization that causes privilege-escalation bugs. TEAM-06 (Phase 9) proves it end-to-end; this phase proves the mechanism.
Output: `apps/api/src/lib/authorization.ts` (ROLE_RANK, ForbiddenError, requireDomainAccess, scopedDomainIds) with a passing real-Postgres unit suite.
</objective>
