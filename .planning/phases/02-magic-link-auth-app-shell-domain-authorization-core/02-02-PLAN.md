## Phase Goal

**As a** team operator, **I want to** sign in to Kurzly with a magic link and land in a themeable dashboard shell whose every domain-scoped action is authorized server-side, **so that** I can manage short links securely on my own infrastructure.

> This plan builds the auth data layer the whole phase stands on: the better-auth instance, the invite-only allowlist gate, the minimal Domain/Membership schema, and the applied migration.

<objective>
Assemble the better-auth `magicLink()` instance (bundled Prisma adapter over db.ts's shared client, SMTP-backed neutral-response `sendMagicLink`), extend `packages/shared` with the Role + auth DTOs, generate the better-auth tables via `@better-auth/cli generate`, add the minimal `Domain` + `DomainMembership` models by hand, and apply it all to live Postgres in a [BLOCKING] migrate/generate step.

Purpose: This is the foundation both the magic-link wiring (02-04) and the authorization core (02-03) depend on. Getting the single-client sharing (Pitfall 2), the in-callback allowlist (D-01), and the applied migration right here means downstream plans are pure wiring + tests.
Output: `lib/auth.ts`, `lib/mailer.ts`, `lib/allowlist.ts`, extended shared DTOs, a schema with 6 new models, a committed migration, and a regenerated client.
</objective>
