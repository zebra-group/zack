# Phase 08 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Deckt ab:** Genau vier Oberflächen, alle **additiv** zu bereits gebautem UI:
- **Surface A** — neue Akkordeon-Sektion „UTM-Parameter" in `LinkFormModal.vue` (3 Inputs + Live-Vorschau der zusammengebauten Ziel-URL, META-01).
- **Surface B** — neue Akkordeon-Sektion „Custom OG-Tags" in `LinkFormModal.vue` (3 Inputs links + 210px Social-Card-Live-Vorschau rechts, META-02).
- **Surface C** — zwei neue Attribut-Badges „UTM" / „OG" in der Links-Tabelle (`LinksView.vue`).
- **Surface D** — zwei neue Chips „UTM-Parameter gesetzt" / „Custom OG-Tags" in der Chips-Zeile der Link-Detailseite (`LinkDetailView.vue`).

Dazu eine **strukturelle Anpassung** am bestehenden Modal: das Akkordeon wird von einem einzelnen Boolean (`secOpen`) auf das im Prototyp gesperrte **exklusive** Drei-Sektionen-Verhalten umgestellt (siehe Decision UI-08-01).

**Nicht in diesem Contract:** Neue Screens, neue Routen, neue Modals, neue Design-Tokens, Änderungen am Modal-Rahmen/Footer/den bestehenden Feldern (Ziel-URL, Domain, Slug, Slug-Warnung, „Passwort & Ablauf", forwardQuery-Toggle, Tracking-Toggle) — die bleiben unverändert. Ebenfalls nicht: UTM `term`/`content`, OG-Bild-**Upload**, Kampagnen-Presets, per-Domain-OG-Defaults, plattformgenaue Social-Crop-Simulation (alle laut `08-CONTEXT.md` deferred), sowie jeder serverseitige Fetch der Ziel-URL oder der OG-Bild-URL (laut D-08-04 **verboten**, nicht nur deferred).

### Ausdrücklich gewaiverte Heuristiken

1. **„Maximal 3–4 Font-Größen"** — gewaivert. Phase 8 führt **keine neue Größe** ein; jede genutzte Größe (9.5 / 10 / 10.5 / 11 / 11.5 / 12 / 12.5 / 13px) stammt aus der in Phase 2 gesperrten Vollskala und wird bereits an anderer Stelle im Produkt gerendert.
2. **„Maximal 2 Font-Gewichte"** — gewaivert. Phase 8 nutzt 400/500/600 aus der LOCKED Gewichts-Menge.
3. **„Alle Spacing-Werte müssen Vielfache von 4 sein"** — gewaivert. Übernommen werden die exakten Prototyp-Feinwerte (`padding:8px 10px` der Inputs, `10px 12px` der Preview-Box, `8px 10px` des Card-Body, 210px Card-Breite, 76px Bildfläche, 3px Card-Zeilen-Gap, 5px Caption-Abstand).
4. **„Empty State / Primary CTA / Destructive Confirmation je Phase"** — teilweise n/a. Phase 8 fügt keinen Screen und keine eigenständige Aktion hinzu; CTA/Empty/Destructive sind daher als „geerbt bzw. entfällt" dokumentiert und in der Copywriting-Sektion begründet, statt neu erfunden zu werden.

### Begründung

Jeder Wert stammt entweder direkt aus dem gesperrten Prototyp (Z.696–738 für die zwei Sektionen, Z.86–89 für die Listen-Badges, Z.1014–1019 für die Detail-Chips) oder aus bereits im Code gesperrten Mustern der Phasen 5–7 (`.security-*`-Akkordeon, `.tracking-badge`, `.chip`, inline Feld-Fehler-Stil, `.helper-text`). > **Explizit: Phase 8 verwendet `--accent` an KEINER Stelle.** Die einzigen Akzentflächen im Modal (Primärbutton „Link erstellen", aktive Toggles) sind bereits ausgeliefert und werden nicht angefasst. Weder ein UTM-/OG-Badge, noch ein Chip, noch die Vorschau-Box, noch die Social-Card, noch ein Sektions-Header darf Akzent tragen. Das ist die konsequente Fortsetzung der Phase-2–7-Disziplin: Akzent = genau eine primäre Aktion pro Fläche + Selektionszustände, sonst nie.

## Interaktions- & Zustands-Contract (phasenübergreifend, verbindlich)

| Zustand | Verhalten |
|---------|-----------|
| Modal öffnet (create) | Alle drei Sektionen zu (`openSection = null`). Alle sechs Felder leer. Zusammenfassungen leer. |
| Modal öffnet (edit) | Alle drei Sektionen zu — **auch wenn Werte gesetzt sind**. Die `· N gesetzt`-Zusammenfassung im Header ist das Signal, dass dort etwas drin ist; das ist exakt das ausgelieferte Phase-5-Verhalten und wird nicht geändert. |
| Sektion öffnen | Schließt die jeweils andere offene Sektion (UI-08-01). Kein Animations-/Transition-Effekt — der Handoff sagt „sonst keine Animationen (bewusst nüchtern)" (README Z.158). |
| Tippen in einem UTM-Feld | UTM-Vorschau + Header-Zusammenfassung aktualisieren synchron. Kein Netzwerkverkehr. |
| Tippen in einem OG-Feld | Social-Card + Header-Zusammenfassung aktualisieren synchron. Kein Netzwerkverkehr **an unseren Server**; ein geänderter Bild-URL-Wert löst einen Browser-Bildrequest an die getippte URL aus. |
| Ungültige OG-Bild-URL (Schema ≠ http/https) | Server lehnt beim Speichern ab → Inline-Fehler unter dem Feld. Die Vorschau versucht ein solches Bild gar nicht erst zu laden und bleibt auf der Schraffur. |
| Absenden | Ein einziger bestehender Submit — es gibt **keinen** separaten „UTM speichern"- oder „OG speichern"-Button. |
| Nach Erfolg | Unverändertes bestehendes Verhalten (Modal schließt, Toast, Liste/Detail aktualisiert) — plus: die neuen Badges/Chips erscheinen ohne Reload, da sie aus dem zurückgegebenen `LinkDTO` abgeleitet werden. |

**Fokuspunkt je Surface (Checker-Nachtrag):** In Surface A ist die Live-Vorschau der zusammengebauten URL der visuelle Anker — die drei Inputs sind die Steuerspalte, die zu ihr hinführt. In Surface B ist die 210px-Social-Card der Anker; die Input-Spalte links ist ihr untergeordnet. Wo Platz knapp wird, weicht die Input-Spalte, nie die Vorschau.

**Bild-Request-Auslöser (Checker-Nachtrag, präzisiert UI-08-10):** Die Textvorschauen aktualisieren synchron pro Tastendruck. Das `<img src>` der Social-Card ist davon ausgenommen: es wird ausschließlich gebunden, wenn der eingegebene Wert als absolute `http:`/`https:`-URL parst, und dieses eine Binding wird um ~300 ms entprellt. Ohne diese Ausnahme würde jeder Tastendruck einen Browser-Request an jeden Teil-Host (`h`, `ht`, `https://ex`, …) auslösen. Solange der Wert nicht parst oder der Ladeversuch scheitert, bleibt die Schraffur stehen.

**Accessibility (Mindestvertrag, konsistent zu Phase 5–7):** Beide neuen Sektions-Header sind per Tastatur erreichbar (`role="button"`, `tabindex="0"`, Enter/Space) und tragen `aria-expanded`. Der bestehende „Passwort & Ablauf"-Header wird im selben Zug angeglichen, da er durch UI-08-04 ohnehin dieselbe Komponente/Klasse nutzt. Die Live-Vorschauen sind rein dekorativ-informativ und benötigen keine Live-Region.
