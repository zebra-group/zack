## Phase Goal

**As a** Kurzly operator, **I want to** enable optional OIDC/SSO login through environment variables — with the admin screen showing whether it is active and the exact callback URL to register — **so that** my team can sign in through our own identity provider while magic-link keeps working unchanged and SSO-provisioned users never inherit admin.

> Derived from the ROADMAP Phase 10 goal line into user-story shape (MVP framing), matching the Phase 7/8/9 autonomous precedent.

<objective>
Expose the read-only SSO-status endpoint that both admin surfaces read (D-10-02, UI-10-02): `GET /api/sso/status` returns the `SsoStatusDTO` derived from the ENV-configured state — enabled flag, issuer, a server-masked client-id, and the real better-auth callback URL to register with the IdP (D-10-06). The client secret is never read, never selected, never returned. This is a status-and-guidance surface, not a credential-entry form: there is deliberately no POST that accepts OIDC credentials from the browser (D-10-02).

Purpose: the single server-authoritative source the TeamView card (10-04) and the LoginView flag (10-05) consume so the UI never re-derives SSO state itself.
Output: routes/sso.ts, its registration in app.ts, and the integration suite proving the secret is excluded and the callback path is real.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API → browser (anonymous + admin) | The status response defines exactly what SSO configuration detail is exposed to any caller; the secret must never cross |
| browser → API | There must be NO inbound path that accepts OIDC credentials from the browser (status is read-only) |

| T-10-NO-CRED-FORM | Tampering | SSO configuration surface | medium | mitigate | there is deliberately no POST/PUT that accepts issuer/client-id/client-secret from the browser — configuration is ENV-only (D-10-02); adding such a route is out of scope and explicitly deferred |
