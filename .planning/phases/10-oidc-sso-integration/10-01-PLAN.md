## Phase Goal

**As a** Kurzly operator, **I want to** enable optional OIDC/SSO login through environment variables — with the admin screen showing whether it is active and the exact callback URL to register — **so that** my team can sign in through our own identity provider while magic-link keeps working unchanged and SSO-provisioned users never inherit admin.

> Derived from the ROADMAP Phase 10 goal line into user-story shape (MVP framing), matching the Phase 7/8/9 autonomous precedent. The ROADMAP goal line is not itself in user-story form; this derivation follows the established autonomous convention rather than halting.

<objective>
Lay the ENV + shared substrate the whole phase stands on: the three optional OIDC env vars with an all-three-or-none boot guard (D-10-07), a single `lib/ssoConfig.ts` reader that is the sole source of truth for SSO config (consumed by auth.ts in 10-02 and the status route in 10-03), the shared `SsoStatusDTO` (D-10-02, UI-10-02), and the `ssoCallbackPath()` / `maskClientId()` / `SSO_PROVIDER_ID` primitives that keep the callback URL and provider id consistent across the backend (D-10-06).

Per D-10-02 this phase configures OIDC via ENV (never a DB-stored, browser-entered credential form). This plan installs the ENV surface for that decision. No new npm dependency is introduced — D-10-01 uses the already-installed better-auth genericOAuth — so no supply-chain legitimacy gate applies.

Purpose: every later plan reads SSO config — this is where it is defined once, safely.
Output: three optional env vars + a partial-config boot guard, `lib/ssoConfig.ts`, `SsoStatusDTO`, and the `.env.example` documentation the drift guard requires.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator ENV/secrets file → API process | OIDC issuer/client-id/client-secret arrive as untrusted operator configuration (ASVS V5); a partial or malformed set must fail loudly at boot |
| shared DTO type → browser | SsoStatusDTO defines exactly what may cross to the client; the client secret must be structurally excluded |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-10-PARTIAL-CONFIG | Denial of Service | env.ts OIDC vars | medium | mitigate | all-three-or-none guard in parseEnv fails boot on a partial OIDC config (D-10-07) — never a half-enabled login path where SSO looks configured but cannot complete |
| T-10-SECRET-SHAPE | Information Disclosure | SsoStatusDTO | high | mitigate | the DTO type has no client-secret field and client-id only ever crosses as clientIdMasked (UI-10-06) — leaking the secret to the browser becomes a TypeScript compile error, not a runtime discipline |

| T-10-NO-INSTALL | Tampering | dependency surface | n/a | accept | no npm/pip/cargo install occurs this phase — D-10-01 uses the already-installed better-auth genericOAuth, so no supply-chain legitimacy gate is required |
