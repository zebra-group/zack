# Phase 03 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Deckt ab:** Domains-Screen innerhalb der bestehenden App Shell (ersetzt den `ComingSoonView`-Platzhalter für `/domains`) — Domain-Liste (Name, Typ-Badge Subdomain/Apex, Status-Badge Pending/Active/Failed, Aktionen), Add-Domain-Zeile mit Subdomain/Apex-Auswahl, pro-Domain-DNS-Anleitungs-Panel (CNAME für Subdomains, A/ALIAS für Apex) mit Copy-to-Clipboard, „Jetzt prüfen"-Verifizierungsaktion mit Status-Übergängen, Empty State, Domain-Entfernen-Bestätigungsdialog.

**Nicht in diesem Contract:** in-app-ACME/TLS-Zertifikatsverwaltung (D-01 — Betreiber-Proxy-Sache, keine Kurzly-UI dafür), der `ask`-/Status-Endpoint selbst (Backend, kein UI-Oberflächenelement), die 404-/Redirect-Auflösungsseiten (Phase 5), Links/QR auf Domains (Phase 4/7), Team-/Domain-Zuweisung pro Mitglied (Phase 9).

**DNS-Verify-Interaktion (State-Übergänge, UI-Anteil):**
- Klick auf „Jetzt prüfen" → Button-Label wechselt kurzzeitig zu „Prüfe …" (disabled, `opacity:.6`) während der Request läuft.
- Bei Erfolg: Status-Badge wechselt sofort auf „Aktiv" (Akzent-Pille), Toast „{domain} verifiziert ✓", Verify-Button verschwindet aus der Zeile, „Zuletzt geprüft"-Zeile aktualisiert sich.
- Bei Fehlschlag (kein/falscher Record gefunden): Status-Badge wechselt auf „Fehlgeschlagen" (bzw. bleibt „DNS ausstehend", falls Backend das so unterscheidet — Planner/Executor entscheiden anhand D-03; UI unterstützt beide Badge-Zustände), Inline-Meldung + „Zuletzt geprüft"-Zeile in `#e5484d`, Verify-Button bleibt sichtbar für erneuten Versuch.
- Bei Rate-Limit (429): Inline-Meldung „Zu viele Prüfungen. Bitte warte kurz, bevor du es erneut versuchst." statt der generischen Fehlschlag-Meldung.
