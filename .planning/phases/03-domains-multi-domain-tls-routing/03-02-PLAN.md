<objective>
Deliver the on-demand DNS verification slice and the remaining owner/admin-gated domain management actions. Builds `dnsClient.ts` (injectable, SSRF-safe, timeout-bounded), adds the `POST /:id/verify`, `DELETE /:id`, and `GET /:id/instructions` routes to `domains.ts`, and threads an injectable resolver through `buildApp` so tests are deterministic and CI never hits live DNS.

Purpose: satisfies DOMAIN-02 (trigger a DNS check → correct record flips to "Active", incorrect leaves it pending/failed) and DOMAIN-04 (per-domain DNS instructions), and closes the SSRF and DNS-DoS threats via DNS-only resolution + a bounded timeout + a per-route rate limit.

Output: `dnsClient.ts` + its unit suite, three new routes with authorization, `buildApp` resolver injection, and expanded integration coverage.

**Decisions covered:**
- **D-02** (Domain-Typen & Verifizierung): both types supported — **subdomains via CNAME** (resolveCname against the fixed documented target) and **apex domains via A-record/ALIAS** (resolve4 against the fixed documented IP); the per-domain instructions (`GET /:id/instructions`, DOMAIN-04) return the record correct for each `DomainType`.
- **D-03** (Domain-Typen & Verifizierung): DNS verification runs as an **on-demand "Jetzt prüfen" action** (a DNS lookup of the expected CNAME/A record) driving the status display (pending/active/failed); it is **SSRF-safe by construction** (DNS resolution only, NO HTTP fetch to arbitrary hosts — enforced by the fetch-spy canary test), timeout-bounded, and rate-limited. Periodic auto-recheck is intentionally deferred (Claude's Discretion, per D-03).
</objective>

## Phase Goal (user story)

**As an** admin, **I want to** click "Jetzt prüfen" and have Kurzly verify my domain's DNS record (and show me the exact record to set), **so that** a correctly-configured domain flips to "Active" and I know precisely what to configure at my DNS provider. (Derived from Phase 3 Success Criteria 2 + 3-instructions, DOMAIN-02/DOMAIN-04.)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API → external DNS resolver | verifyDomain issues DNS queries for an operator-supplied hostname |
| browser → verify/delete/instructions | admin action + session cookie cross here; mutate a domain's lifecycle |

## STRIDE Threat Register (ASVS L1, block on high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering / EoP | dnsClient.verifyDomain (SSRF surface) | high | mitigate | DNS resolution only via `node:dns/promises`; no HTTP/fetch to the domain (asserted by the SSRF-canary fetch-spy test). |
| T-03-03b | Elevation of Privilege | verify / delete / instructions routes | high | mitigate | `requireDomainAccess(prisma, userId, id, 'admin')` on all three; ForbiddenError → 403; deny-by-default for unknown user/domain (proven by a member-role 403 test). |
| T-03-05 | Denial of Service | POST /:id/verify (DNS amplification) | medium | mitigate | Per-route `VERIFY_RATE_LIMIT` (10/5min); DNS lookup bounded by a `Promise.race` 5s timeout so a hung nameserver can't pin a worker. |
| T-03-07 | Spoofing / EoP | domain-hijack via stale DNS record reuse | medium | accept | MVP: verification requires a fresh passing check at claim time (standard for this product class); a future enhancement may auto-revert status on delete — noted, not blocking. |
</threat_model>
