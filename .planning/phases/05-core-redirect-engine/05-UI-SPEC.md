# Phase 05 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Deckt ab:** Die drei öffentlichen, server-gerenderten HTML-Seiten außerhalb des Dashboard-SPA-Bundles — Passwort-Seite (UI-04, REDIR-04), Ablauf-Seite (UI-05, REDIR-03), generische 404-Seite (REDIR-02/D-11) — sowie die Erweiterung des bestehenden Link-Erstellen-/Bearbeiten-Formulars (`LinkFormModal.vue`) um Passwort/Ablaufdatum/Query-Weitergabe (D-01/D-12). Zusätzlich der strukturelle (nicht-visuelle) Kontrakt für den Bot/OG-HTML-Pfad (REDIR-05, D-05/D-06).

**Nicht in diesem Contract:** Custom-OG-Tags pro Link (Titel/Beschreibung/Bild, META-02 — Phase 8), reales Klick-Tracking/Analytics (Phase 6, hier nur die Naht D-17), dynamisches QR-Remapping (Phase 7), UTM-Builder-UI (bereits Phase 4 in Ziel-URL eingebacken, hier unverändert).

**Registry-Safety-Gate entfällt** (wie Phase 2/3/4 — kein shadcn im Spiel).

### NEU in Phase 5: Theme-Mechanismus für öffentliche Seiten

Die Dashboard-SPA schaltet Light/Dark über ein `data-theme`-Attribut + Pinia-Store (Cookie/localStorage, an eine eingeloggte Session gebunden). Die 3 öffentlichen Seiten haben **keine Session, kein Client-JS, keinen Store** (D-09) — ein Besucher, der auf `/passwort-geschuetzter-slug` landet, hat keinen Theme-Toggle zur Verfügung. Deshalb:

- **Theme folgt `prefers-color-scheme` (OS-Präferenz) via CSS `@media`-Query**, nicht `data-theme`. Kein sichtbarer Toggle auf den öffentlichen Seiten (Claude's Discretion, deckt D-10 "Light/Dark" ab, ohne eine nicht vorhandene Session-Persistenz vorzutäuschen).
- Die exakten Farbwerte (Light/Dark) sind identisch zu `apps/web/src/styles/tokens.css` — **1:1 kopiert**, nicht neu erfunden (siehe Color-Sektion unten für den vollständigen `<style>`-Block).

### NEU in Phase 5: Branding-Konfiguration (D-10)

`D-10` verlangt konfigurierbaren Brandname/Akzent über "bestehende Prototyp-Props/ENV". Es existiert noch **kein** `BRAND_NAME`/Akzent-ENV im Projekt (`apps/api/src/env.ts` geprüft — nicht vorhanden). Phase 5 führt daher neu ein:

| ENV | Default | Scope |
|-----|---------|-------|
| `BRAND_NAME` | `"Kurzly"` | Nur die neue server-gerenderte Public-HTML-Schicht (Passwort-/Ablauf-/404-Seite + Bot-OG-HTML). **Nicht** rückwirkend in die bereits ausgelieferte Dashboard-SPA verdrahtet (Phase 2/3/4 sind abgeschlossen; Retrofit wäre Scope-Creep) |
| `BRAND_ACCENT` | `#d7ff01` | Gleicher Scope wie oben — überschreibt `--accent` nur im inline `<style>`-Block der Public-Seiten |

Beide optional mit Fail-Safe-Default (Muster identisch zu `CNAME_TARGET`/`A_RECORD_IP` in `env.ts`, D-Ansatz aus Phase 3) — eine frische Instanz bootet unverändert ohne Konfiguration.

`brandInitial` = erster Buchstabe von `BRAND_NAME`, uppercased (identisch zur Prototyp-Formel `brand.slice(0,1).toUpperCase()`, Prototyp Z.1110).

## Design-Fidelity Waiver / Constraint Exceptions

> **Diese Sektion gilt unverändert weiter (aus Phase 2 übernommen, projektweit gültig, solange der gesperrte Handoff gilt). Checker und Auditor: die unten gelisteten Phase-5-spezifischen Typografie-/Spacing-Werte sind KEINE Verstöße, sondern verbindliche, prototyp-/musterabgeleitete Tokens.**

### Standing Sign-Off (unverändert aus Phase 2/3/4)

- Requirement **UI-03**, Locked Decision **D-04 (Phase 2)**, `.claude/CLAUDE.md` **„UI-Treue: High-Fidelity … pixelgenau nach Prototyp."** — stehende Projekt-Owner-Freigabe für 1:1-Reproduktion der Prototyp-Tokens, auch für Phase 5.

### Ausdrücklich gewaiverte Heuristiken (weiterhin gültig)

1. **„Maximal 4 Font-Größen"** — gewaivert. Phase 5 führt **keine neue Font-Größe** ein — jede hier genutzte Größe stammt aus der in Phase 2 gesperrten Vollskala (9.5–52px).
2. **„Maximal 2 Font-Gewichte"** — gewaivert. Phase 5 nutzt 400/600/700 aus der LOCKED Gewichts-Menge.
3. **„Alle Spacing-Werte müssen Vielfache von 4 sein"** — gewaivert. Phase 5 übernimmt die exakten Prototyp-Feinwerte der Besucher-Overlay-Screens (Kartenpadding `30px 26px`/`34px 26px`, Icon-Kachel 52px, Chip-Radius 7px u. a. — siehe Spacing Scale unten).

### Bewusste Abweichungen vom rohen Prototyp-Markup (dokumentiert, nicht versehentlich)

Der Prototyp zeigt die 3 Besucher-Seiten als **In-Canvas-Overlay-Previews** innerhalb des Design-Tools (mit einem „✕ Vorschau schließen"-Link und einer erklärenden Fußzeile „Öffentliche Seite · so sehen Besucher…"). Diese Artefakte sind **Design-Tool-Chrome**, keine Produkt-Copy, und entfallen 1:1 in der echten Implementierung — es gibt aus einem eigenständigen öffentlichen HTML-Dokument keine "Vorschau zu schließen". Konkret:

| Prototyp-Artefakt | Behandlung in Phase 5 |
|---|---|
| „✕ Vorschau schließen" (alle 3 Seiten) | **Entfällt vollständig.** Kein Zurück-Navigationselement — der Besucher kam über einen direkten Link/QR-Scan, es gibt keinen "Zurück zum Dashboard" |
| „Öffentliche Seite · so sehen Besucher …" Fußzeile (Passwort-/Ablauf-Seite) | **Ersetzt** durch dieselbe `.footer-text`-Komponente wie `LoginView.vue`/`AuthErrorView.vue` (11px, `--mut`, zentriert): **„{{brand}} · self-hosted"** — konsistente Selbstauskunft auf jeder eigenständigen öffentlichen Seite der App (Login/Auth-Fehler/Passwort/Ablauf/404) |
| Passwort-Seite hat **keine** Marken-Zeile (Logo+Name), 404-Seite **hat** eine | **Vereinheitlicht:** alle 3 öffentlichen Seiten erhalten dieselbe Marken-Zeile (Logo-Kachel + `{{brand}}`) wie die 404-Seite bzw. wie `LoginView.vue`/`AuthErrorView.vue` — musterabgeleitet, nicht roh übernommen. Begründung: die fehlende Marken-Zeile bei Passwort/Ablauf im Prototyp ist ein Artefakt der Canvas-Kompaktheit der Overlay-Demo, kein bewusster Produktentscheid; ein echter Besucher, der auf einer fremden Subdomain landet, profitiert auf **jeder** Seite von klarer Markenidentität (Vertrauenssignal, kein Phishing-Anschein) |
| „Demo-Passwort: sommer2026"-Hinweis | **Entfällt vollständig** — reines Design-Tool-Demo-Datum, kein Produkt-Text |
| Passwort-Seite: „Entsperrt ✓"-Zwischenzustand mit sichtbarem Klartext-Ziel nach korrektem Passwort | **Entfällt als eigener gerenderter Zustand.** D-07 legt fest: korrektes Passwort → Server antwortet auf den POST direkt mit **HTTP 302** (kein zusätzlicher 200-Zwischenschritt mit "Weiterleitung läuft…"-Anzeige). Der Prototyp simuliert diesen Zustand nur, weil eine Canvas-Demo keinen echten Server-Redirect ausführen kann. Kein Leak-Risiko durch das Weglassen — im Gegenteil, es entfernt eine unnötige Zwischenseite |

### Begründung

Jeder Token stammt entweder direkt aus der gesperrten Prototyp-Quelle (`Kurzly Prototyp.dc.html` Zeilen 496–574, 740–757) oder — wo diese Phase server-seitige Sicherheitsanforderungen (No-Leak, D-07/D-14) oder eine andere Auslieferungsform (eigenständiges HTML-Dokument statt In-App-Overlay) hat, die der Prototyp so nicht abbildet — aus bereits gesperrten Prototyp-**Mustern** anderer Screens (`LoginView.vue`/`AuthErrorView.vue`-Kartenschale, Marken-Zeile, Fußzeile). Keine Ad-hoc-Erfindung.

**Sicherheits-/Interaktionskontrakt (No-Leak-Anker, D-07/D-14 — hier bindend für die Visual-Ebene):**

- Die `GET`-Antwort enthält **an keiner Stelle** des HTML, keinem HTTP-Header, keinem HTML-Kommentar, keinem `data-*`-Attribut das echte Ziel (`targetUrl`). Auch nicht in auskommentierter/versteckter Form (`display:none`, JSON-LD, Meta-Tag). Der `.url-chip` zeigt ausschließlich die **aufgerufene** Kurz-URL (`{{domain}}/{{slug}}`), niemals das Ziel.
- Das `<form>` sendet ein natives `POST` (kein Fetch/XHR nötig, kein Client-JS erforderlich — funktioniert auch ohne JavaScript) an einen Verify-Endpoint.
- **Falsches Passwort:** Server rendert **dieselbe** Seite erneut (`errorState=true`), Inline-Fehler erscheint, Input-Border wird `#e5484d`. Auch diese Fehler-Antwort enthält das Ziel nicht.
- **Korrektes Passwort:** Server antwortet **direkt mit HTTP 302** auf das echte Ziel + `Set-Cookie` (Session-Cookie, link-gebunden, D-08) — **kein** separater 200-„Entsperrt"-Zwischenschritt wird gerendert (siehe Waiver-Tabelle oben).
- **Rate-Limit (D-15):** bei Überschreiten liefert der Verify-Endpoint 429 mit dem Standard-Fehlertext (siehe Copywriting) — als einfache Text-/JSON-Antwort ausreichend, kein eigenes gestaltetes HTML nötig (kein Requirement dazu).

- Diese Präzedenzstufe steht **vor** dem Passwort-Gate (D-14): ein abgelaufener UND passwortgeschützter Link zeigt immer die Ablauf-Seite, nie die Passwort-Seite.

### 4. Bot/OG-HTML-Pfad (REDIR-05, D-05/D-06) — strukturell, NICHT visuell gestaltet

Kein eigenständiger, für Menschen gestalteter Screen — dieser Hinweis stellt sicher, dass Planner/Executor keinen vierten visuellen Seitentyp bauen. Kontrakt:

- Erkannter Bot/Crawler (User-Agent-Bibliothek, D-04) erhält **immer** `HTTP 200` mit einem minimalen `<head>`, der generische OG-Meta-Tags trägt (`og:title`, `og:description`, `og:image`, `og:url` — generisch = `{{brand}}`-Werte, D-05, **nicht** die späteren Custom-OG-Werte aus META-02).

- `<body>` kann leer/minimal bleiben (Crawler liest primär `<head>`); falls ein sichtbarer Fallback-Body gewünscht ist, reuse einfach die 404-Karten-Shell mit generischer Copy — kein neues Design nötig.
