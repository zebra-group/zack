## Phase Goal

**As a** Kurzly admin, **I want to** invite teammates with a chosen role, assign members specific domains, change roles, and remove people — while trusting that every member can only see and edit the Links, QR codes, and Analytics of their assigned domains, enforced server-side — **so that** I can safely delegate link management without ever exposing another domain's data.

> Derived from the ROADMAP Phase 9 `**Goal:**` line into user-story shape (MVP framing), matching the Phase 7/8 precedent. The ROADMAP goal line is not itself in user-story form; this derivation follows the established autonomous convention rather than halting.

<objective>
Lay the account-role foundation the whole phase stands on: a new global `AccountRole` enum + `User.accountRole` column (D-09-01), the better-auth wiring so the session carries `accountRole` (UI-09-02), the seeded admin becoming an account admin, the shared `SessionUser.accountRole` DTO field, and a single reusable `isAccountAdmin` primitive that both the authorization-helper bypass (plan 09-02) and the team routes (plans 09-03/09-04) import.

Purpose: every later plan in this phase reads `accountRole` — this is the substrate.
Output: one additive migration, one new enum, one defaulted column, the better-auth `additionalFields` wiring, an account-admin seed, `SessionUser.accountRole`, and `lib/accountRole.ts`.
</objective>

## Trust Boundaries

| Boundary | Description |

| DB migration → live schema | A new enum + defaulted column must backfill every existing better-auth-owned `user` row without data loss |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-ROLE-MASS | Elevation of Privilege | better-auth user.additionalFields.accountRole | high | mitigate | `input: false` on the additionalField + `disableSignUp: true` — a client cannot set its own accountRole through any auth/signup path; the only writers are admin-seed and the admin-gated team routes (09-04) |
| T-09-SEED-LOCKOUT | Denial of Service | admin-seed accountRole | medium | mitigate | Seed sets accountRole=admin on both create and update so an operator always has at least one account admin — the D-09-07 lockout invariant's precondition |
| T-09-MIGR-BACKFILL | Tampering | add_user_account_role migration | medium | mitigate | Column is `@default(member)` so every pre-existing row backfills to the least-privileged role; no existing user is silently elevated |
| T-09-SESSION-STALE | Information Disclosure | get-session accountRole | low | accept | The session field is a UX convenience (nav/guard); the server re-checks accountRole server-side on every team/admin action (09-03/09-04), so a stale client value never grants access |
</threat_model>
