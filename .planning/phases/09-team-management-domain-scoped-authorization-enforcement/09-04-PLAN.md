<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → PATCH/PUT/DELETE /api/team/:id | Admin-only role/domain/removal mutations cross into the API |
| removal → content ownership | Deleting a user must not delete the links/QR codes that belong to the domain, not the person |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-MUT-AUTHZ | Elevation of Privilege | team mutation routes | high | mitigate | Every mutation gates on isAccountAdmin server-side; member callers receive 403 regardless of the UI; proven per-route |
| T-09-LOCKOUT | Denial of Service | remove/demote last admin | high | mitigate | countAdmins guard on removeMember + changeMemberRole("member") returns LAST_ADMIN and makes no change; three D-09-07 cases pinned by tests |
| T-09-PROMOTE-RACE | Tampering | promote-to-admin | medium | mitigate | The membership delete + accountRole update run in one prisma.$transaction (D-09-05) so no partial "admin still scoped to a domain" state can persist |
| T-09-REMOVE-CONTENT | Tampering | removeMember | medium | mitigate | Relies on schema Cascade (memberships) + SetNull (Link.creator) — a test asserts the removed user's Link survives with createdBy null (D-09-06); no manual, error-prone cleanup |
| T-09-MUT-MASS | Tampering | mutation request bodies | medium | mitigate | Zod allowlists { accountRole } / { domainIds } only; request.body never reaches Prisma directly |
</threat_model>
