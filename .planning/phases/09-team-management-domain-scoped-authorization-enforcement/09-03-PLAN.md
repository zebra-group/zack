## Phase Goal

**As a** Kurzly admin, **I want to** invite teammates with a chosen role, assign members specific domains, change roles, and remove people — while trusting that every member can only see and edit the Links, QR codes, and Analytics of their assigned domains, enforced server-side — **so that** I can safely delegate link management without ever exposing another domain's data.

</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → GET/POST /api/team | Admin-only team reads and invites cross into the API; a non-admin must be refused server-side |
| invite email → magic-link sender | An admin-supplied address becomes an allowlisted User row and receives a login link |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-TEAM-AUTHZ | Elevation of Privilege | GET/POST /api/team | high | mitigate | Every team endpoint gates on isAccountAdmin server-side (09-01), returning 403 for members regardless of what the UI offers; proven by the member-403 tests |
| T-09-INVITE-MASS | Tampering | invite request body | high | mitigate | Zod allowlist { email, accountRole, domainIds } — request.body never reaches Prisma directly; accountRole is a fixed enum, no id/emailVerified injectable |
| T-09-INVITE-BOMB | Denial of Service | POST /api/team/invite | medium | mitigate | MAGIC_LINK_RATE_LIMIT applied to the invite route (it triggers a mail send) — same posture as the login magic-link endpoint |
| T-09-STATUS-DRIFT | Information Disclosure | status derivation | medium | mitigate | status is computed only from emailVerified at the API boundary and shipped as an explicit field; the pending->active round-trip test fails loudly if better-auth ever stops setting emailVerified on verify (D-09-03) |
| T-09-INVITE-DUP | Tampering | re-invite path | low | mitigate | Re-invite looks the address up first and never re-creates or re-roles an existing user; a test asserts no duplicate and unchanged accountRole |
</threat_model>
