## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session role → nav + route visibility | The client hides the Team surface from members; this is UX only — the server (09-03/09-04) refuses regardless |
| API response → rendered roster | TeamView renders only the server-provided, admin-authorized member list |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-UI-BOUNDARY | Elevation of Privilege | nav filter + route guard | medium | mitigate | Hiding the nav and redirecting members is explicitly UX convenience (T-02-14 precedent); the server-side admin gate on /api/team (09-03) is the real boundary, so a member bypassing the guard still gets 403 and no data |
| T-09-STATUS-REDERIVE | Information Disclosure | status badge | low | mitigate | The badge reads the DTO status field verbatim, never recomputing from emailVerified — a test asserts this, so the UI can never diverge from the server's derived truth (D-09-03/UI-09-08) |
| T-09-ROSTER-SCOPE | Information Disclosure | listTeamMembers render | low | accept | The team roster is intentionally full-instance data, shown only to an account-admin (server-gated); no per-domain scoping applies to the team list itself |
</threat_model>
