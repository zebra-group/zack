<objective>
Re-prove the password gate (REDIRECT-E2E-02) end-to-end through a REAL browser session — the one requirement whose signed, httpOnly, path-scoped unlock-cookie round-trip is most naturally proven with a real cookie jar (12-CONTEXT.md locked decision: use `page`, not `request`, here). A wrong password must be rejected with the LOCKED inline error, a correct password must free the link and redirect, and the target must never appear in any pre-unlock response.

Because a real browser CANNOT set a forbidden `Host` header via `page.goto`, this plan targets the registered redirect domain by navigating to `http://e2e.kurzly.local:3000/...` with a Chromium host-resolution rule mapping `e2e.kurzly.local → 127.0.0.1` — a hermetic, offline-runnable technique that avoids mutating `/etc/hosts` and resolves the STATE blocker ("confirm custom-domain testing approach: /etc/hosts vs. host-header") for the browser path. This is a strictly harder version of the APIRequestContext Host-header approach the Wave 0 spike proved for the API specs, so this plan self-validates its browser mechanism in Task 1 before exercising the full flow in Task 2.

This phase writes ZERO application code — no task touches `apps/api/src`. Playwright's `page` API cannot read the httpOnly signed cookie VALUE by design, so all assertions are on navigation OUTCOME (12-RESEARCH.md `unlockCookie.ts` note), never on decoding the cookie.

Purpose: Prove the password gate's no-leak + self-invalidating-unlock contract over a real browser cookie jar against the built image.
Output: `redirect-password-gate.spec.ts`.
</objective>
