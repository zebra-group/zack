## Phase Goal

**As a** Kurzly operator, **I want to** enable optional OIDC/SSO login through environment variables — with the admin screen showing whether it is active and the exact callback URL to register — **so that** my team can sign in through our own identity provider while magic-link keeps working unchanged and SSO-provisioned users never inherit admin.

> Derived from the ROADMAP Phase 10 goal line into user-story shape (MVP framing), matching the Phase 7/8/9 autonomous precedent.

<objective>
Build the admin-facing half of the phase: the "Authentifizierung" section on TeamView (10-UI-SPEC Surface A), two cards inserted between the roster table and the role-model card (UI-10-01). The Magic Link card is descriptive; the OIDC/SSO card is a read-only status + setup-guidance surface driven verbatim by GET /api/sso/status (D-10-02 — NOT a credential-entry form). Add the `getSsoStatus()` api client and the minimal router escape hatch that makes "Login-Seite ansehen →" actually render /login for an authenticated admin (UI-10-09 resolution).

Reuses existing locked building blocks (the card shell, .status-badge, .dns-code-block, .copy-button + copyToClipboard, the toast) — Phase 10 introduces no new token, color, size, or weight (10-UI-SPEC Design System).
Purpose: the admin sees whether SSO is active and the exact callback URL to register with their IdP (AUTH-05 surface).
Output: getSsoStatus(), the TeamView Authentifizierung section, the /login preview guard, and their tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| status DTO → admin browser render | The OIDC card may render only the fields present on SsoStatusDTO; nothing sensitive may be re-derived or unmasked client-side |
| router guard → view render | The /login preview escape hatch decides whether an authenticated admin sees the login form — a UX boundary only, never a security boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-10-CARD-SECRET | Information Disclosure | OIDC card render | high | mitigate | the card renders only SsoStatusDTO fields (enabled/issuer/clientIdMasked/callbackPath) verbatim and never unmasks; the DTO has no secret field, so there is nothing sensitive to leak into the DOM (UI-10-06) |
| T-10-CARD-FALSE-STATE | Information Disclosure | ssoStatus null fallback | low | mitigate | a failed status fetch renders a neutral fallback and neither Aktiv nor Deaktiviert, so the UI never asserts a false SSO state (UI-10-02) |
