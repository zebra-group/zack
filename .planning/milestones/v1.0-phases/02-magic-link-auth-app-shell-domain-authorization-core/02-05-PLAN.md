## Phase Goal

**As a** team operator, **I want to** sign in to Kurzly with a magic link and land in a themeable dashboard shell whose every domain-scoped action is authorized server-side, **so that** I can manage short links securely on my own infrastructure.

> This plan delivers the client half of magic-link login (the pixel-accurate Login + error pages, AUTH-01/D-05), the theme engine (UI-02/UI-03 tokens), and the session store the App Shell will consume.

<objective>
Build the theme engine (LOCKED CSS custom-property tokens + Geist fonts + Pinia theme store with localStorage persistence), the authSession Pinia store (session fetch/logout), the typed auth API client, and the two public auth views (Login Idle/Sent, Magic-link error) exactly per the UI-SPEC LOCKED layouts.

Purpose: These are the user-facing entry points and the theme foundation the whole App Shell (02-06) reuses. Pixel fidelity here (UI-03) and the neutral Sent-state copy (D-01) are the load-bearing requirements.
Output: theme.ts + authSession.ts stores, api.ts auth client, tokens.css + fonts, LoginView + AuthErrorView, and component tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser JS → session cookie | httpOnly cookie is not readable by client JS (XSS mitigation) — store reflects server state only |
| login form → /api/auth | Untrusted email submitted from the browser |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-11 | Information Disclosure | Magic-link error page reveals failure reason | medium | mitigate | AuthErrorView shows one generic message for expired/used/invalid (D-05); no target/account leak |
| T-02-12 | Information Disclosure | Login Sent-state copy leaks account existence | high | mitigate | Sent-state copy is identical regardless of allowlist status (D-01) — component test asserts the neutral message |
| T-02-13 | Spoofing | Client store treated as auth boundary | low | accept | authSession store is UX only; the API re-verifies the httpOnly session on every request (documented) |
</threat_model>
