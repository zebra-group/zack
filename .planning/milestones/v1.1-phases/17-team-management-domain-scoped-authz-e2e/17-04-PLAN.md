No production code change is anticipated.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| zero-domain member browser -> GET /links/:id, /api/qr-codes/:id, /api/links/:id | IDOR boundary — a direct-by-id request for an out-of-scope resource must 404 (no existence oracle) |
| zero-domain member browser -> GET /api/analytics | scoping boundary — the rollup must narrow to the member's (empty) domains, never leak another tenant's clicks |
| public internet -> GET /:slug (redirect handler) | the real click that seeds a baseline-domain ClickEvent the member must not see |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-04-IDOR | Information disclosure / Elevation of Privilege | resolveOwnedLink/resolveOwnedQrCode 404-for-both | high | mitigate | This spec PROVES the guard at the E2E layer for the first time: a zero-domain member gets a 404 (never a 403 that reveals existence, never a 200 leak) on direct-by-id Link/QR requests; a regression fails the assertion |
| T-17-04-SCOPELEAK | Information disclosure | GET /api/analytics scopedDomainIds narrowing | high | mitigate | This spec PROVES a real click on an unowned domain is absent from the member's rollup (empty 200) — a scoping regression that widened the rollup to all links would fail the empty-topLinks/clicks30Days-0 assertion |
| T-17-04-ORACLE | Information disclosure | choosing 404 vs 403 for out-of-scope resources | medium | accept | The 404-for-both design is deliberate (no existence oracle); the spec asserts 404 exactly and must not be "fixed" to a 403, which would reintroduce an existence oracle |
</threat_model>
