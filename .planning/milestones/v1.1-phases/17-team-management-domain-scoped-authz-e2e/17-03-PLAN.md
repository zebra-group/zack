<objective>
Prove TEAM-E2E-03 end-to-end through two real browser contexts: removing a member immediately revokes their active session — on the member's very next request, not merely at the next login attempt. 17-RESEARCH.md establishes this as a code-verified, schema-level guarantee (the strongest-evidence finding in the file): `Session.user onDelete: Cascade` + `removeMember`'s single `tx.user.delete()` + better-auth's uncached `getSession` (no `cookieCache`) mean the very next `getSession()` after removal reads a row that is already gone. The spec therefore keeps the removed member's SAME context open and asserts the FIRST subsequent request fails — no polling, no cookie re-injection (Pitfall 4). The proof is threefold: `GET /api/auth/get-session` returns null (API boundary), a dashboard navigation redirects to /login (UI/route guard), and a direct-Prisma cross-check confirms the User row and all its Session rows are gone.

This spec asserts REAL, currently-passing behaviour — `lib/team.ts`'s removeMember, `schema.prisma`'s cascade, better-auth's getSession, `routes/team.ts`, `TeamView.vue`, and the router guard were all read in full during research and need no changes. If a genuine app-code gap surfaces (an unexpected RED — e.g. the session survives), STOP and flag it as a task; do NOT weaken an assertion (Phase 11-16 TDD RED->GREEN precedent). No production code change is anticipated.
