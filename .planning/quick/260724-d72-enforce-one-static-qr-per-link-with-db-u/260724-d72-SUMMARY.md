# Quick Task 260724-d72: Enforce one static QR per Link (DB-level) Summary

**Partial unique index `QrCode_linkId_static_key` (raw-SQL migration) makes the DB the authoritative guarantee for "at most one static QR per Link", surfaced as a new `QR_ALREADY_EXISTS` / HTTP 409 conflict from `createQrCode` — closing v1.0 tech-debt item WR-09.**

## Performance

- **Duration:** ~15 min
- **Completed:** 2026-07-24T09:46:00+02:00
- **Tasks:** 2 (Task 1 non-TDD migration; Task 2 TDD RED→GREEN)
- **Files modified:** 5 (1 created, 4 modified)

## Accomplishments
- Added a hand-authored raw-SQL Prisma migration (`20260724074120_enforce_one_static_qr_per_link`) creating a partial unique index on `QrCode.linkId` scoped to `WHERE variant='static'`, preceded by a non-destructive duplicate-data guard that fails fast with an actionable message rather than a cryptic Postgres error.
- Verified the migration applies cleanly via `prisma migrate deploy` against a fresh, throwaway `postgres:18-alpine` container (11/11 migrations applied; index confirmed via `\d QrCode`), then verified it also applies inside the real test harness (globalSetup's testcontainers Postgres).
- Documented the raw-SQL partial index in `schema.prisma`'s `QrCode` model comment so a future `prisma migrate dev` preserves it instead of treating it as drift.
- Added `QR_ALREADY_EXISTS` to `QrCodeErrorCode`, mapped it to HTTP 409 in `statusForQrError`, and taught `createQrCode` a two-layer defense: a `findFirst` friendly pre-check for `static` creates (mirrors `createLink`'s `resolveSlug` pattern) plus a variant-branched P2002 race catch, so dynamic `code` collisions are unaffected (still `CODE_GENERATION_EXHAUSTED`).
- `routes/qrCodes.ts` required and received zero changes — its existing `reply.code(statusForQrError(result.error)).send({ error: result.error })` automatically surfaces the new 409.

## Decisions Made
- Migration timestamp `20260724074120` generated via `date -u +%Y%m%d%H%M%S` at execution time, sorting after the last committed migration (`20260723061259_add_user_account_role`).
- The duplicate-data guard is a PL/pgSQL `DO $$ ... END $$` block using `string_agg` to name every offending `linkId` in a single `RAISE EXCEPTION` — chosen over a bare `CREATE UNIQUE INDEX` so an operator upgrading from a pre-WR-09 install with (unlikely, since uniqueness was previously frontend-only) pre-existing duplicates gets an actionable message instead of a cryptic Postgres constraint-violation error.
- The P2002 catch in `createQrCode` branches purely on the already-validated `variant` (not by inspecting the Postgres error's constraint name) — sufficient because a `static` create can only ever collide on the new partial index, and a `dynamic` create can only ever collide on `code`'s pre-existing unique constraint; no ambiguity between the two causes exists.
