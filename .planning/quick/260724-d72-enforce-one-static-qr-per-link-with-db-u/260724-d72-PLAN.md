<objective>
Close the v1.0 milestone tech-debt item WR-09 (Phase 7): the "at most one static QR code per
Link" invariant is currently enforced ONLY by application logic / a frontend client-side check
(07-09 decision: LinkDetailView does a `listQrCodes()` + client-side variant/linkId filter) — there
is NO database-level guarantee. A direct API call or a race between two concurrent POSTs can create
two static QR codes for the same Link.

This plan makes the database the authoritative guarantee (a partial unique index on `QrCode.linkId`
scoped to `variant = 'static'`, added via a raw-SQL Prisma migration because Prisma's `@@unique`
cannot express a `WHERE` condition) and surfaces a new conflict error code (`QR_ALREADY_EXISTS` /
HTTP 409) from the existing QR-creation path — following the codebase's established
`QrCodeErrorCode` + `statusForQrError` pattern and mirroring `createLink`'s `resolveSlug`
friendly-fast-path + P2002-catch defense-in-depth.

Purpose: Guarantee the one-static-QR-per-link invariant at the only layer that can enforce it under
concurrency and direct-API access, with a precise, client-actionable conflict error.
Output: A backward-compatible additive migration, the new backend conflict error, and integration
tests (real Postgres) proving both the DB rejection and the 409 route response.

SCOPE GUARD: A separate, parallel quick task adds a QR-delete path — this plan MUST NOT touch any
delete logic. Stay scoped to the uniqueness constraint + conflict error. The frontend already
guards this case client-side (07-09); wiring a frontend 409 message is explicitly OUT OF SCOPE
here (the backend 409 is the defense-in-depth guarantee for API/race callers).
</objective>

Reference facts already established during planning (do not re-derive):
- `isUniqueConstraintViolation(err)` is EXPORTED from apps/api/src/lib/links.ts (checks err.code ===
  "P2002" structurally). It is ALREADY imported and used in lib/qrCodes.ts's createQrCode catch.
- The precedent to mirror: lib/links.ts's `createLink` uses `resolveSlug` (a `findFirst` pre-check
  that returns a friendly SLUG_TAKEN before the insert) AND a P2002 catch after the insert (race
  defense) — the DB `@@unique([domainId, slug])` is the real guarantee, the pre-check is the
  friendly-error fast path. This plan applies the SAME two-layer pattern to static QR uniqueness.
- Prisma CANNOT express a partial/filtered unique index in schema.prisma (no `WHERE` on `@@unique`).
  A plain `@@unique([linkId])` would be WRONG — it would forbid dynamic QRs and multiple dynamic QRs
  on the same link, both of which the design ALLOWS. The index MUST be raw SQL and partial.
- `prisma migrate dev` refuses to run non-interactively on confirmation-shaped warnings (03-01) and
  cannot GENERATE a raw-SQL-only partial index anyway — so this migration is HAND-AUTHORED and
  applied/verified via `prisma migrate deploy` against a throwaway `postgres:18-alpine` container on
  a host port (03-01 / 07-02 precedent), NOT the docker-compose db service (no host port mapping).
- Because a partial unique index is not representable in schema.prisma, a future `prisma migrate dev`
  run would see it as drift — a schema.prisma comment must document that it is intentionally raw-SQL.
- The QR package set (qrcode/sharp/jsqr) is already installed and signed off (07-01, T-07-SC). This
  plan adds NO dependencies — no supply-chain / package-legitimacy gate applies.
