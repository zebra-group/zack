<objective>
Fix the tech-debt bug IN-01: LinkDetailView.vue's edit-modal submit path silently drops `trackingEnabled`. Toggling or preserving tracking through the "✎ Bearbeiten" flow on the link detail screen never reaches the API.

Root cause (confirmed by reading the code): the bug is in `apps/web/src/views/LinkDetailView.vue`, in TWO places that together break the edit-modal tracking flow. LinkFormModal.vue already emits `trackingEnabled` correctly (its submit payload includes `trackingEnabled: trackingEnabled.value`), and LinksView.vue already handles it correctly — LinkDetailView is the lone outlier:

1. The `<LinkFormModal>` binding (around lines 547-567) does NOT pass `:initial-tracking-enabled`, unlike LinksView.vue (line 436). LinkFormModal's `withDefaults(..., { initialTrackingEnabled: true })` therefore forces the modal's internal toggle to ON regardless of the link's real state.
2. `handleEditSubmit` (around lines 296-343) neither declares `trackingEnabled` in its payload type nor forwards it into the `updateLink(...)` call, so the emitted value is discarded.

The correct, in-repo reference is `apps/web/src/views/LinksView.vue`: it passes `:initial-tracking-enabled="editTarget.trackingEnabled"`, declares `trackingEnabled?: boolean` in its `handleEditSubmit` payload type, and forwards `trackingEnabled: payload.trackingEnabled` to `updateLink`. This fix mirrors that exact pattern in LinkDetailView. `UpdateLinkInput` already accepts `trackingEnabled?: boolean` (LinksView compiles against it today).

Purpose: Make the link detail edit modal's tracking toggle actually functional and non-destructive, closing carried tech-debt IN-01 (Phase 6).
Output: A fixed LinkDetailView.vue plus red-then-green component tests proving the field is preserved and applied.
</objective>
